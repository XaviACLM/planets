     const DEFAULT_TIME_DELTA_MS = 60 * 1000; // 1 minute
     const MS_PER_DAY = 24 * 60 * 60 * 1000;
     
     function signedAngleDifference(from: number, to: number): number {
     	let diff = to - from;
     	while (diff > Math.PI) diff -= 2 * Math.PI;
     	while (diff < -Math.PI) diff += 2 * Math.PI;
     	return diff;
     }
     
     function computeVelocity(base: NodePositions, progressed: NodePositions, node: Node, timeDeltaMs: number): number {
     	return signedAngleDifference(base.get(node), progressed.get(node)) / (timeDeltaMs / MS_PER_DAY);
     }
     
     function computeAllVelocities(base: NodePositions, progressed: NodePositions, timeDeltaMs: number): Map<Node, number> {
     	const velocities = new Map<Node, number>();
     	for (const [node] of base.getPositions()) {
     		velocities.set(node, computeVelocity(base, progressed, node, timeDeltaMs));
     	}
     	return velocities;
     }

     	const changed: Node[] = [];
     	for (const [node, pos] of newPositions.getPositions()) {
     		if (oldPositions.getPositions().get(node) !== pos) {
     			changed.push(node);
     		}
     	}
     	return changed;
     }

     	nodes: Node[]

### Assistant

You're right about `false || someExpensiveComputation()` — that's short-circuit evaluation and JS absolutely does skip the right side. That's a language-level guarantee.

But `useState(someExpensiveComputation())` is different. There's no short-circuiting here. It's just a normal function call:

```ts
const result = someExpensiveComputation(); // runs first
useState(result);                          // then this receives the value
```

JS evaluates arguments before passing them to functions. `useState` has no way to prevent that — by the time it receives the value, the computation already happened. `useState` just internally ignores the argument after the first render (it returns the stored state instead), but the argument was still computed.

That's exactly why the `() =>` lazy initializer form exists:

```ts
useState(() => someExpensiveComputation());
```

Here you're passing a *function* to `useState`, which is cheap. `useState` then decides whether to *call* that function — it only calls it on the first render and skips it on subsequent renders.

So to summarize: not a JS quirk, not a React quirk, just standard function call semantics. Arguments are evaluated before the function can do anything about them.

**On the core design question — how to express cross-object dependencies:**

Your instinct is right. The changeXYZ pattern already works well for this. The key insight you already landed on: objects take dependencies as parameters at construction/change time but don't store references. The constructor says "I need these values to build myself." The change methods say "something external changed, here's the new value, give me an updated copy." Both are stateless with respect to the dependency — no live link.

I agree that HCP currently keeping a `_zsp` reference is a bit at odds with this philosophy. It works fine since everything's immutable, but it does blur the line.

**On naming — a few ideas:**

1. **Keep `change` for everything.** `NP.changeDignityMode(mode, hcp, zsp)`, `NP.changeHouseCuspPositions(hcp)`. The word "change" just means "something changed, give me an updated self." It doesn't matter whether the thing that changed is internal config or an external dependency. This is consistent with what you already have and honestly reads fine.

2. **`withUpdated`** — `NP.withUpdatedHouseCusps(hcp)`, `HCP.withUpdatedZodiacSigns(zsp)`. Reads as "a version of me reflecting updated X." More explicit about the external nature. Slightly verbose.

3. **`afterChangeIn`** — `NP.afterChangeInHouseCusps(hcp)`. Makes the reactive nature very clear — "this is me *after* something else changed." Probably too wordy.

4. **Split the naming**: keep `change` for internal config (`changeLunarNodeMode`, `changeDignityMode`) and use a different verb for reacting to external dependency updates (`updateFromHouseCusps`, `applyHouseCusps`). This makes the distinction explicit but introduces two conventions where one might suffice.

I think that's fine. A named type with a comment makes the semantics explicit, and the filter function keeps the messiness contained to one place:

```ts
/** Values of null indicate that the node should be removed from positions. */
type PositionPatch = Map<Node, number | null>;

function applyPatch(positions: Map<Node, number>, patch: PositionPatch): Map<Node, number> {
	const result = new Map(positions);
	for (const [node, value] of patch) {
		if (value === null) result.delete(node);
		else result.set(node, value);
	}
	return result;
}
```

Then all the change methods just do `applyPatch(this._positions, computeWhatever(...))`. The null semantics are documented once, handled once, and everything downstream stays `Map<Node, number>`. Honestly more succinct than either the `set/remove` approach or the raw spread pattern you have now.

You're right to question it — but unfortunately there really is no pure CSS way to uniformly scale arbitrary HTML content like an SVG. SVGs get this for free via `viewBox`, but HTML has no equivalent. CSS can make things *reflow* (wrap, shrink columns, etc.) but not *scale down uniformly while preserving proportions*.

That said, ResizeObserver is not complicated at all. It's just "call this function whenever this element's size changes." The whole thing is ~10 lines:

```tsx
const [scale, setScale] = useState(1);
const containerRef = useRef<HTMLDivElement>(null);

useEffect(() => {
    const el = containerRef.current;
    if (!el) return;
    const obs = new ResizeObserver(([entry]) => {
        setScale(Math.min(1, entry.contentRect.width / NATURAL_WIDTH));
    });
    obs.observe(el);
    return () => obs.disconnect();
}, []);
```

Then `transform: scale(scale)` on the table. It's the standard way to do this — nothing exotic. I wasn't jumping the gun, it's just that "scale HTML like an SVG" requires a tiny bit of JS because CSS doesn't have that concept natively.

### Assistant

It's a great question and there's a real reason. CSS `transform` is purely **visual** — it happens in the paint phase, *after* layout. When you `scale(0.5)` a div, the browser still reserves the original full-size space for it in the layout. Other elements don't reflow around the scaled version. It's like drawing it smaller while the "hole" it occupies stays the same.

This isn't an oversight — it avoids circular dependencies. Imagine a built-in "scale to fit container" property. For an SVG, this is well-defined: the geometry is fixed, scaling is just multiplying coordinates. But HTML content *reflows*. A paragraph at 500px wide has a different height than at 300px wide. So if the browser tried to auto-scale:

1. Compute natural size → 600px wide, 400px tall
2. Container is 400px → scale to 0.67
3. But wait, at 0.67x, the content is effectively at 400px wide, which reflows text differently, changing the natural height...
4. Which changes what needs scaling...

It's circular. The ResizeObserver approach works precisely because we break the loop manually: measure the container (layout phase), compute a ratio (JS), apply a visual-only transform (paint phase), and crucially the transform *doesn't feed back into layout*.

SVG avoids this because its content model doesn't reflow. That's the fundamental difference — not a missing feature, but a consequence of HTML being a reflowing document format.

### Assistant

CSS `mask-image` with a gradient. It's one property and it does exactly what you want — the element itself (including its backdrop-filter effect) gradually fades to transparent at the edges:

```css
mask-image: linear-gradient(
    to bottom,
    transparent, black 20px,
    black calc(100% - 20px), transparent
);
```

This feathers the top and bottom edges over 20px. The blur smoothly dissolves into the sharp background — no hard boundary. You can do all four sides by layering two gradients (horizontal + vertical) with `mask-composite: intersect`.

It's not complicated at all and I think it'll look quite natural — the blur just melts away at the edges. Want me to add it?
