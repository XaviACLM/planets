ZODIAC POSITIONS REFACTOR SPEC
===============================

Goal: Split the ZodiacPositions god object into four focused immutable classes,
and update all call sites.

NAMING DECISIONS
----------------
- "Zodiac Symbol" -> "Zodiac Sign" (everywhere in the codebase)
- "AstrologyMode" -> "ZodiacMode" (everywhere: type, enum, settings, UI)
- "astrologyUtil.ts" -> "chartAnalysis.ts"
- "houses.ts" -> "houseCuspPositions.ts" (computation logic stays in-file)
- The four new classes: NodePositions, HouseCuspPositions, ZodiacSignPositions, FixedStarPositions

DESIGN PHILOSOPHY
-----------------
- All four classes are immutable. Config values (date, surfacePosition, lunarNodeMode,
  etc.) are private (prefixed with _). Each class exposes only what external code needs.
- chartAnalysis.ts functions throw errors on nonsensical inputs rather than returning
  null. E.g. isNodeEastern throws if nodePositions has no surface position;
  getHouseOfNode throws if houseCuspPositions is null. HouseCuspPositions.create
  throws if surfacePosition is null (caller must check before calling).


PHASE 1: EXTRACT HELPER FUNCTIONS
----------------------------------
Move from zodiacPositions.ts to astronomyUtil.ts:
  - computeLunarApogeePerigeeMeeus
  - computeLunarApogeePerigeeExact
  - computeLunarNodesMeeus
  - computeLunarNodesExact
Also move getTodayEclipticLongitudeFromEQJ to astronomyUtil.ts (general-purpose
coordinate conversion, used by both nodePositions.ts and houseCuspPositions.ts).

The dispatchers (computeLunarApogeePerigee, computeLunarNodes) stay with
NodePositions — dispatching by LunarNodeMode is a domain decision, not astronomy.


PHASE 2: CREATE THE FOUR CLASSES
---------------------------------

2A. FixedStarPositions (new file: fixedStarPositions.ts)
  - Simplest of the four.
  - Depends entirely on: date
  - No changeXYZ methods (date change = full recompute)
  - Private state: _date, _positions: Map<string, number>
  - Public: getPositions(), getPosition(name)
  - Constructor takes date, optional precomputed positions.

2B. ZodiacSignPositions (new file: zodiacSignPositions.ts)
  - Depends entirely on: date, zodiacMode
  - No changeXYZ methods (both inputs cause full recompute — the whole point
    of the split is that we no longer need to track cross-object dependencies)
  - Private state: _date, _zodiacMode, _signPositions: Map<Zodiac, number>
  - Public state: siderealOffset: number | null
  - Public methods:
      getSignPositions(): Map<Zodiac, number>
      isRegular(): boolean  (was isZodiacModeRegular)
      getSignAtLongitude(lon): Zodiac  (was _getSymbolAtLongitude)
      getPositionWithinSign(lon): number  (takes raw longitude, not Node)
  - Note: getSignOfNode does NOT live here (it needs NodePositions). It becomes
    a free function getSignOfNode(node, nodePositions, zodiacSignPositions) in
    chartAnalysis.ts.
  - Computation functions (private/local to file):
      computeSiderealOffset, computeZodiacSignPositionsFromSiderealOffset,
      computeZodiacSignPositionsForIrregularMode

2C. HouseCuspPositions (new file: houseCuspPositions.ts)
  - houses.ts is renamed to houseCuspPositions.ts. All house computation logic
    stays in-file — nobody else needs to know how houses are computed.
  - Depends entirely on: date, surfacePosition, houseSystem
  - Depends partially on: zodiacSignPositions (only matters for house systems in
    AyanamsaDependantHouseSystems, which already exists in current houses.ts)
  - Depends partially on: housePresweep (stored config, no cusp recomputation,
    but changeHousePresweep returns a new instance via copyWith for immutability)
  - Can be null at the call site: when surfacePosition is null, or when the house
    system is undefined for the position/time (Placidus/Koch at extreme latitudes).
    HouseCuspPositions.create itself throws if surfacePosition is null — the caller
    is responsible for checking.
  - computeHouseCuspPositions no longer depends on NodePositions (see Phase 3).
  - changeHouseSystem(newSystem, zodiacSignPositions): full cusp recompute
  - changeHousePresweep(newValue: boolean): copyWith, no cusp recomputation
  - changeZodiacSignPositions(newZSP): recomputes cusps only if houseSystem is in
    AyanamsaDependantHouseSystems. Otherwise returns this.
  - Private state: _date, _surfacePosition, _houseSystem, _housePresweep,
    _cuspPositions: number[]
  - Public methods:
      getCuspPositions(): number[]
      getCuspPosition(i): number
      getHouseOfNode(lon: number): number  (takes longitude, not Node; presweep logic here)
      areHouseCuspsWithinHouse(): boolean
        -- returns true if housePresweep is false OR no house is narrower than 5 degrees

2D. NodePositions (new file: nodePositions.ts)
  - The beefiest one. Keeps most helper functions from current zodiacPositions.ts.
  - Depends entirely on: date, surfacePosition
  - Depends partially on: lunarNodeMode, hamburgSchoolMode
  - changeLunarNodeMode(newMode): recomputes lunar nodes + apogee/perigee only
  - changeHamburgSchoolMode(newMode): recomputes hamburg school objects only
  - Private state: _date, _surfacePosition, _lunarNodeMode, _hamburgSchoolMode,
    _positions: Map<Node, number>
  - Public methods:
      getPositions(): Map<Node, number>
      get(node): number  (was getNodePosition)
      has(node): boolean
      hasSurfacePosition(): boolean
  - Note: isAboveHorizon and isEastern do NOT live here. NodePositions truly just
    stores positions. These become free functions in chartAnalysis.ts.
  - Contains/imports the compute functions:
      computePhysicalNodePositions, computeSmallObjectPositions,
      computeHamburgSchoolObjectPositions, computeAxisAngles,
      computeEquinoxes, computeArabicPartPositions,
      computeAllNodePositions, computeAllNodePositionsWithoutSurfacePosition
  - Contains the LunarNodeMode/HamburgSchoolMode dispatchers:
      computeLunarNodes, computeLunarApogeePerigee
  - Imports from astronomyUtil.ts:
      computeLunarNodesMeeus, computeLunarNodesExact,
      computeLunarApogeePerigeeMeeus, computeLunarApogeePerigeeExact


PHASE 3: REMOVE computeHouseCuspPositions DEPENDENCY ON NODE POSITIONS
-----------------------------------------------------------------------
In houseCuspPositions.ts (was houses.ts), refactor computeHouseCuspPositions:
  - Remove the knownNodes parameter
  - Systems that need ASC/DSC/MC/IC as ecliptic longitudes (Porphyry, Placidus,
    Koch, etc.) call computeAllSignificantPoints + getTodayEclipticLongitudeFromEQJ
    internally to get the AxisAngles struct.
  - Space-based systems continue working exactly as they already do (they call
    computeAllSignificantPoints internally for their own needs).
  - The dispatcher (computeHouseCuspPositions) only dispatches. It does not try
    to share computeAllSignificantPoints calls between systems.
  - getTodayEclipticLongitudeFromEQJ is imported from astronomyUtil.ts.

Resulting signature:
  computeHouseCuspPositions(date, surfacePosition, houseSystem, zodiacSignPositions): number[] | null
(This signature is unchanged by the partial zodiacSignPositions dependency
optimization — that logic lives in changeZodiacSignPositions, which decides
whether to call this function at all.)


PHASE 4: DELETE ZodiacPositions, RENAME astrologyUtil.ts
---------------------------------------------------------
- Delete zodiacPositions.ts
- Rename astrologyUtil.ts -> chartAnalysis.ts
- Update all imports

chartAnalysis.ts will contain free functions that operate across position objects:
  - getChartSect(nodePositions) -> Sect
  - isInSect(node, nodePositions) -> boolean | null
  - getChartRuler(nodePositions, zodiacSignPositions, dignityMode) -> Node | null
  - getAngleProximity(node, nodePositions) -> AngleProximityInfo
  - isTrailing(trailingNode, leadingNode, nodePositions) -> boolean
  - isNodeAboveHorizon(node, nodePositions) -> boolean  (moved from NodePositions)
  - isNodeEastern(node, nodePositions) -> boolean  (moved from NodePositions)
  - getHouseAngularities(nodePositions, houseCuspPositions, houseAngularityMode) -> ...
  - getFixedStarsWithinLongitude(node, nodePositions, fixedStarPositions, maxDist) -> ...
  - getHouseOfNode(node, nodePositions, houseCuspPositions) -> number
    (convenience: pulls lon from nodePositions, calls houseCuspPositions.getHouseOfNode)
  - getSignOfNode(node, nodePositions, zodiacSignPositions) -> Zodiac
    (convenience: pulls lon from nodePositions, calls zodiacSignPositions.getSignAtLongitude)
  - getNodePositionWithinSign(node, nodePositions, zodiacSignPositions) -> number
    (same pattern)
  All these functions throw on nonsensical inputs (see Design Philosophy above).


PHASE 5: GLOBAL RENAME
------------------------
- "AstrologyMode" -> "ZodiacMode" everywhere (type, enum values, settings store,
  settings UI, variable names). Files affected: astroDefs.ts, settingsDefs.ts,
  settingsStore.ts, settingsMenus.tsx, App.tsx, zodiacSignPositions.ts,
  houseCuspPositions.ts, dignities.ts, any UI that displays mode names.
- "zodiac symbol" / "zodiacSymbol" -> "zodiac sign" / "zodiacSign" everywhere
  (variable names, type names, comments). Notably getZodiacSymbolPositions ->
  getSignPositions, etc.


PHASE 6: REFACTOR App.tsx
---------------------------
Replace single zodiacPositions state with four:
  const [nodePositions, setNodePositions] = useState(...)
  const [houseCuspPositions, setHouseCuspPositions] = useState<HouseCuspPositions | null>(...)
  const [zodiacSignPositions, setZodiacSignPositions] = useState(...)
  const [fixedStarPositions, setFixedStarPositions] = useState(...)

Full recompute on date/city change:
  useEffect(() => {
    const newNodePositions = NodePositions.create(selectedDate, selectedCity, lunarNodeMode, hamburgSchoolMode)
    const newZSP = ZodiacSignPositions.create(selectedDate, zodiacMode)
    setNodePositions(newNodePositions)
    setZodiacSignPositions(newZSP)
    setFixedStarPositions(FixedStarPositions.create(selectedDate))
    setHouseCuspPositions(selectedCity !== null
      ? HouseCuspPositions.create(selectedDate, selectedCity, houseSystem, newZSP, housePresweep)
      : null)
  }, [selectedCity, selectedDate])

Partial recompute effects:
  useEffect(() => {
    setNodePositions(prev => prev.changeLunarNodeMode(lunarNodeMode))
  }, [lunarNodeMode])

  useEffect(() => {
    setNodePositions(prev => prev.changeHamburgSchoolMode(hamburgSchoolMode))
  }, [hamburgSchoolMode])

  useEffect(() => {
    const newZSP = ZodiacSignPositions.create(selectedDate, zodiacMode)
    setZodiacSignPositions(newZSP)
    setHouseCuspPositions(prev => prev?.changeZodiacSignPositions(newZSP) ?? null)
  }, [zodiacMode])

  useEffect(() => {
    setHouseCuspPositions(selectedCity !== null
      ? HouseCuspPositions.create(selectedDate, selectedCity, houseSystem, zodiacSignPositions, housePresweep)
      : null)
  }, [houseSystem])

  useEffect(() => {
    setHouseCuspPositions(prev => prev?.changeHousePresweep(housePresweep) ?? null)
  }, [housePresweep])

Walk through every component/file that currently takes zodiacPositions and replace
with the specific objects it needs:

    needs: nodePositions, zodiacSignPositions

    needs: nodePositions, zodiacSignPositions

    functions take specific position objects as described in Phase 4

    - rulershipGraph depends on nodePositions + zodiacSignPositions + dignityMode
